前言

前面幾天，筆者陪大家把「放手讓 agent 寫入」這件事講透了：[Day 20] 一起學怎麼審 `side_effects` 再點頭，[Day 21] 把 GitHub App 與 push-to-deploy 全自動化跑通。到這裡，一個人操作 0ops 的能力其實已經齊全。但筆者自己在專案裡待久了就發現，真實情況很少是一個人——一旦專案進到團隊，就會冒出兩個問題：**誰能做什麼**（權限），以及**誰做了什麼**（稽核）。

筆者覺得這兩件事其實是一體兩面。你給 member 開了刪 app 的權限，事後就得查得到是誰在半夜三點把正式環境砍了。反過來，如果稽核記錄查不到執行者，那再嚴的權限設計也只是紙上談兵。今天這篇，筆者想跟大家把這兩面一起看清楚。

今天要弄懂三件事：

- owner / admin / member / viewer 四個角色各能碰什麼；
- 怎麼用 `0ops audit` 查「誰、在什麼時候、做了什麼」；
- 權限如何延伸到稽核查詢本身——viewer 只查得到自己，admin 才看得到全團隊。

角色是什麼，先看你自己在哪一格

在談「誰能做什麼」之前，你得先知道自己是什麼角色。`0ops teams list` 會把你在每個團隊的身分列出來：

```sh
$ 0ops teams list
```

```
TEAM_SLUG    TEAM_NAME        ROLE     PLAN
acme         Acme Inc.        owner    pro
side-lab     Side Lab         member   free
```

在 `acme` 這個團隊你是 owner，在 `side-lab` 你只是 member。角色是**綁在團隊上的**，不是全域身分——同一個帳號在不同團隊可以有完全不同的權限。

要看整個團隊有哪些成員、各自什麼角色，用 `0ops members list`：

```sh
$ 0ops members list --team acme
```

```
USER_ID                GITHUB_LOGIN    EMAIL                ROLE
u_01H8...              alice           alice@acme.com       owner
u_01H9...              bob             bob@acme.com         admin
u_01HA...              carol           carol@acme.com       member
u_01HB...              dave            dave@acme.com        viewer
```

四個角色能做什麼

0ops 的角色分四級。與其硬記表格，不如記住背後的分界線：**能不能改東西、能不能管人、能不能看到全團隊的稽核**。

| 能力 | owner | admin | member | viewer |
|---|---|---|---|---|
| 看 app / log / 狀態（唯讀） | ✅ | ✅ | ✅ | ✅ |
| 建立 / 重新部署 app | ✅ | ✅ | ✅ | ❌ |
| 刪除 app | ✅ | ✅ | ✅ | ❌ |
| 邀請 / 移除成員 | ✅ | ✅ | ❌ | ❌ |
| 裝 / 移除 GitHub App | ✅ | ✅ | ❌ | ❌ |
| 查全團隊稽核（`audit list` 不限 actor） | ✅ | ✅ | ❌ | ❌ |
| 查自己的稽核（`--actor me`） | ✅ | ✅ | ✅ | ✅ |
| 集中撤權（`sso deprovision`） | ✅ | ❌ | ❌ | ❌ |

幾個要記住的分界：

- **viewer 是純唯讀**：看得到 app、看得到 log，但所有寫入操作（create / redeploy / delete）都做不了。適合稽核人員、客戶端的旁觀者。
- **member 能部署、不能管人**：這是日常開發者的預設角色。能把 app 建起來、redeploy、甚至刪掉自己團隊的 app，但碰不到「邀人 / 踢人 / 裝 GitHub App」這些團隊層級的動作。
- **admin 能管人**：成員邀請、移除、GitHub App 安裝都要 admin 以上。
- **owner 是最高權**：多了一項別人沒有的能力——集中撤權 `0ops sso deprovision`（一次撤掉某人的 membership 加上他所有 token）。這個離職 / 資安事件的殺手鐧留到 [Day 28] 細講。

稽核查詢：誰做了什麼

權限決定「能不能做」，稽核回答「做了沒、誰做的」。0ops 每一個寫入操作都會落一筆 audit log。查詢入口是 `0ops audit list`：

```sh
$ 0ops audit list --since 24h --action create_app
```

```
ID          ACTION        ACTOR            TARGET            TRACE_ID       CREATED_AT
a_01HC...   create_app    carol            app:web-demo      tr_9f3a...     2026-07-06T02:14:07Z
a_01HD...   create_app    alice            app:api-gw        tr_71bd...     2026-07-05T18:02:51Z
```

常用的過濾旗標：

- `--since` / `--until`：時間窗（`--since 24h`、`--since 2026-07-01`）。
- `--action`：只看某類動作（`create_app`、`delete_app`、`redeploy` 等）。
- `--actor`：只看某個執行者。特別的是 `--actor me`——只看自己做的事，這是**任何角色**都能用的。
- `--trace`：用 trace-id 把同一次操作的所有相關記錄串起來。
- `--page-size`（最大 200）、`--cursor`、`--all`：翻頁。

要看某一筆的完整細節，用 `0ops audit get <id>`：

```sh
$ 0ops audit get a_01HC...
```

```
id:          a_01HC...
action:      create_app
actor:       carol (u_01HA...)
target:      app:web-demo
trace_id:    tr_9f3a...
result:      success
created_at:  2026-07-06T02:14:07Z
metadata:
  team_slug:   acme
  source:      github.com/acme/web-demo
  deploy_run:  run_44c1...
```

注意 `actor` 欄位——不只是人。push-to-deploy 觸發的自動 redeploy，actor 會是 `system:github_webhook`（[Day 14] 提過）。稽核要能區分「人做的」和「系統自動做的」，這欄就是關鍵。

權限也管到稽核本身

這是一個容易被忽略、但設計上很要緊的點：**稽核查詢本身也受權限管制**。

- **admin / owner** 用 `0ops audit list` 不加 `--actor` 時，看得到整個團隊所有人的記錄。
- **member / viewer** 沒有全團隊稽核權。他們能查的只有自己——實務上就是加 `--actor me`。

同樣的規則也反映在 MCP 端。給 AI agent 用的唯讀工具 `query_audit_log`：**全團隊查詢需要 admin**；如果呼叫者是 viewer，就只能查 `actor=me`，而且回傳結果會**脫敏**。也就是說，就算你讓 agent 幫你查稽核，它拿到的資料範圍也不會超過你本人的權限——權限不因入口（CLI 或 MCP）而異，這是 0ops 一貫的保證。

用 trace-id 串一次操作的完整軌跡

單看一筆 audit log 只是一個點。真正有用的是把「一次操作牽動的所有記錄」串起來，這靠的是 `trace_id`。

假設 carol 建了一個 app，你想看這次操作到底連帶做了哪些事。先從 `audit list` 找到那筆的 trace-id，再用 `--trace` 撈全部：

```sh
$ 0ops audit list --trace tr_9f3a...
```

```
ID          ACTION           ACTOR    TARGET             CREATED_AT
a_01HC...   create_app       carol    app:web-demo       2026-07-06T02:14:07Z
a_01HE...   deploy_started   system   run:run_44c1...    2026-07-06T02:14:09Z
a_01HF...   deploy_succeeded system   run:run_44c1...    2026-07-06T02:16:33Z
```

一次 `create_app`，背後牽出「開始部署 → 部署成功」兩筆系統記錄，全部掛在同一個 trace-id 底下。事後要回溯「這個 app 是誰、什麼時候、怎麼上線的」，一條 trace 就講完整個故事。

補充一點狀態：0ops 的 audit log 另有 **export / verify** 機制（tamper-evidence，防竄改），這部分已經落地。更完整的稽核與合規操作——匯出、驗證、事故（incident）管理——留到 [Day 29] 專門講。至於 SOC2 / DPA 這類合規認證，目前仍在規劃中，還不能宣稱已具備。

總結

今天把權限與稽核這一體兩面接了起來：四個角色（owner / admin / member / viewer）劃出「誰能做什麼」，`0ops audit list` / `get` 回答「誰做了什麼」，而稽核查詢本身也受權限管制——viewer 只查得到自己，admin 才看得到全團隊。記住這條原則：**能做什麼，要對得上查得到誰做了**。
