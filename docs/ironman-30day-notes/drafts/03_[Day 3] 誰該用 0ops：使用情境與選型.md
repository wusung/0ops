前言

前兩天 [Day 1] 筆者講了「為什麼 AI agent 需要 0ops」，[Day 2] 直接帶大家看了一個 30 秒的部署 demo，相信你對這套工具已經有了初步的感覺。但在花時間裝它、學它之前，筆者覺得有個更該先問的問題：**你到底該不該用 0ops？**

坦白說，筆者自己也踩過「看到新工具就想全都學一遍」的坑。後來才慢慢體會到，好工具不是功能越多越好，而是有沒有對到自己的約束。所以今天不談功能清單，而是想從「你是誰、你卡在哪」出發，陪大家對號入座。

今天大概會聊到三件事：

- 三種最典型、最適合用 0ops 的人；
- 三種「其實不太需要 0ops」的情況；
- 一張可以照著勾的選型決策清單。

三種對號入座

**第一種：個人 side project，想快速上線。**

如果你是那種週末會開新 repo、腦子裡永遠有五個想做的小專案的人（筆者就是），那你的痛點大概不是「部署做不出來」，而是「每個專案都要重走一次部署儀式，煩」。你希望的是：寫完，一句話丟上線，拿到一個能分享的網址。

0ops 對你的價值：`0ops apps create --slug demo --source ./my-app` 一行，或在 AI CLI 裡說一句話，就上線。不用每個專案都重寫一份 K8s manifest。

**第二種：小團隊，想少維護 K8s。**

假設你們有三五個工程師，跑著幾個線上服務。大家都知道 K8s 很強，但沒有人想當那個全職顧 YAML、修 ingress、追 cert-manager 的人。你要的是「部署這件事別再吃掉一個人的心力」。

0ops 對你的價值：把 build、推映像、產 manifest、GitOps、上網域整條管線包起來，你只面對 `0ops apps` 這一層。團隊協作、角色權限（owner/admin/member/viewer）、稽核也都內建，不用自己拼一套。

**第三種：enterprise，要 self-host + 稽核。**

如果你在一個有合規壓力的組織，資料不能出自己的機房，每個部署動作都要查得到「誰在什麼時候做了什麼」，那公有雲的代管平台對你來說大概是不能碰的選項。

0ops 對你的價值：整套可以自架在你自己的 K3s 上（[Day 26] 起會帶你做），而且內建稽核（`0ops audit list` / `get`）。

台灣團隊的特殊情境

如果你在台灣做產品，還有幾個現實考量會把你推向 0ops：

- **台幣計費**：不用每個月盯著美元匯率換算雲端帳單。
- **資料落地**：自架讓資料留在你指定的機房，滿足在地法規對資料位置的要求。
- **合規需求**：金融、醫療、公部門相關的專案，往往硬性要求 self-host 與可稽核。

這幾點是 Vercel、Railway 這類純代管、以美元計價的服務比較難直接滿足的。

什麼情況「不」需要 0ops

筆者一直覺得誠實比推銷重要。以下幾種情況，0ops 對你的邊際效益其實不高：

- **你已經深度綁定某一朵雲。** 如果你的整套架構已經長在 AWS/GCP 的託管服務上（RDS、Lambda、Cloud Run 全都用了），硬要換一層抽象反而是負擔。0ops 補的是「從原始碼到上線」這段，不是要你搬家。
- **你沒有用 AI CLI 的習慣。** 0ops 最亮的那一半是「AI agent 原生入口」。如果你完全不用 Claude Code / Codex 這類工具，那你拿到的只是一個還不錯的 CLI 部署工具，少了一半價值。（不過人類用 CLI 這條路也完整可用，見 [Day 6]。）
- **你只是要放一個純靜態站。** 一個 landing page、一份文件站，丟 GitHub Pages 或 Cloudflare Pages 就好，殺雞不用牛刀。

還有一點要先講清楚的邊界：**0ops 的 production 路徑需要你自備一些外部資源**（K3s host、Cloudflare zone、GitHub OAuth App 等）。它不是「註冊帳號就有一切」的全代管黑箱。這是 self-host 的本質，[Day 26] 會完整列前置清單。

一張選型決策清單

把下面這幾題快速勾一遍，就大致知道 0ops 適不適合你：

| 問題 | 你的答案 |
|---|---|
| 你會用 Claude Code / Codex / Copilot 這類 AI CLI 寫 code 嗎？ | 是 → 大加分 |
| 你希望「部署」這件事別再吃掉一個人的心力嗎？ | 是 → 加分 |
| 你有 self-host / 資料落地 / 稽核的硬需求嗎？ | 是 → 0ops 的主場 |
| 你在台灣、需要台幣計費嗎？ | 是 → 加分 |
| 你已經深度綁定某一朵雲的託管服務了嗎？ | 是 → 收益有限 |
| 你只是要放純靜態站嗎？ | 是 → 用不到 |

勾下來，如果前四題你點頭的多、後兩題都搖頭，那 0ops 大概值得你花這 30 天認識。

一個判斷原則

選型的時候，筆者自己最容易掉進的坑就是「比誰功能多」。但後來慢慢發現，功能多不等於適合自己——適合你的工具，是**對到你約束的那一個**。

所以不妨先問自己：我最大的約束是什麼？是速度（想快點上線）、是心力（不想顧 K8s）、還是合規（資料不能出機房）？把約束想清楚，選型的答案往往就浮出來了。這也是 [Day 4] 之後、一路到 [Day 5] 選型對照的主軸。

總結

今天筆者沒講任何功能，而是想陪大家判斷「你是不是 0ops 的對象」：個人快速上線、小團隊減負、enterprise 自架稽核是三大主場；已綁定某雲、不用 AI CLI、純靜態站則收益有限。台灣團隊還有台幣計費與資料落地的加分。

判斷完「該不該用」，明天 [Day 4] 筆者想回到 [Day 2] 那個最關鍵的疑問：既然要放手讓 AI 執行部署、甚至刪除，那道 preview/confirm 的安全網到底是怎麼運作的？為什麼 agent 繞不過去？
