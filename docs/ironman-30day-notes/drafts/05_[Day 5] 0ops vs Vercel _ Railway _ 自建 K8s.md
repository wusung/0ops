前言

[Day 3] 我們判斷了「誰該用 0ops」，[Day 4] 拆了讓你敢放手的 preview/confirm 安全網。今天把 0ops 放到擂台上，和大家最熟的三個對手比一比：**Vercel、Railway、自建 K8s**。

但先講清楚今天的立場：這不是一篇「0ops 全面勝出」的業配。每個工具都有它的主場，重點是**用你的使用情境當軸**去比，而不是攤一張功能清單比誰項目多。誠實交代 0ops 的邊界，也是這篇的一部分。

今天你會得到三件事：

- 一組從「需求」出發的四維對照；
- 每個對手各自的勝場在哪；
- 一張「照你的約束勾選 → 指向建議」的決策表。

四個對照維度

功能清單能列一百項，但真正決定選型的通常就這四個軸：

1. **AI 原生接入**：你的 AI agent 能不能直接呼叫部署能力，還是永遠要一個人去點瀏覽器？
2. **self-host 能力**：能不能整套裝在你自己的機器上，資料不出機房？
3. **計費在地化**：能不能台幣計價、不看美元匯率臉色？
4. **學習曲線**：從零到第一個服務上線，要學多少東西？

我們用這四個軸掃過四個選項。

Vercel 的勝場

Vercel 是前端／全端框架部署的天花板體驗。如果你做的是 Next.js、Nuxt、SvelteKit 這類，連 GitHub、push 就自動部署，preview deployment、邊緣網路、影像最佳化全都開箱即用，學習曲線幾乎是零。

它的邊界：**強綁定它的代管平台**，沒有真正的 self-host；計費以美元為主；AI 接入是圍繞「人在 dashboard 操作」設計的，不是給 agent 程式化呼叫的原生介面。適合「前端專案、要最順的體驗、不在意資料落地」的人。

Railway 的勝場

Railway 是「後端服務快速上線」的甜點區。你有一個 API、一個 worker、要順便來個 Postgres，Railway 讓你點幾下就串起來，體驗比 Vercel 更偏後端、比 K8s 友善太多。

它的邊界：一樣是**代管、美元計價、沒有你能掌握的 self-host**；AI 接入同樣不是原生設計。適合「後端小服務、要快、不想碰基礎設施」的人。

自建 K8s 的勝場

自己搭一套 K8s（配 ArgoCD、cert-manager、ingress、監控）是**控制力的天花板**。什麼都能調、什麼都在你手上、資料完全落地、想接什麼計費就接什麼。合規和客製需求極高時，這是唯一能滿足到底的路。

它的邊界：**學習曲線陡到勸退**，而且要養一個持續維護它的人。你得自己把 build、推映像、產 manifest、GitOps、網域、TLS 這條管線全部拼出來並長期顧著。控制力的代價是心力。適合「有專門的平台團隊、客製需求極高」的組織。

0ops 的勝場

0ops 想站的位置很明確：**把自建 K8s 的自主性，包成接近 Railway 的體驗，再加上 AI 原生入口。**

- **AI 原生接入**：部署能力以 MCP 工具暴露，agent 直接呼叫（[Day 2] 那個 demo），這是四個選項裡唯一為 agent 而生的介面。
- **self-host**：整套可裝在你自己的 K3s 上（[Day 26] 起），資料落地。
- **計費在地化**：面向台灣團隊，台幣計費。
- **學習曲線**：你主要只面對 `0ops apps` 這一層，底下的 K8s 管線被包起來了。

四維對照表

| 維度 | Vercel | Railway | 自建 K8s | 0ops |
|---|---|---|---|---|
| AI 原生接入 | 弱（為人設計） | 弱（為人設計） | 無（要自己接） | **強（MCP 原生）** |
| self-host | 無 | 無 | **完全** | **可自架 K3s** |
| 計費在地化 | 美元為主 | 美元為主 | 自己決定 | **台幣** |
| 學習曲線 | **極低** | **低** | 高 | 中（自架前置較多） |

沒有一列全贏的選項——這正是重點。

誠實話：0ops 目前的邊界

如果只講勝場，這篇就變業配了。0ops 有幾個你該先知道的邊界：

- **production 路徑需自備外部資源**：K3s host、Cloudflare zone、Cloudflare Tunnel token、GitHub OAuth App、kubeseal 等前置要你備妥（[Day 26] 會列完整清單）。它不是「註冊就有一切」的全代管黑箱。
- **部分能力仍在規劃中**：SOC2/DPA 等合規認證、部分 audit export 細節屬規劃中，不是已到位的既成品；本系列凡遇這類能力都會標狀態，不會說成已具備。
- **CLI 尚未全覆蓋**：例如自訂網域目前 CLI 只有 `0ops domains list`，新增／驗證還在 API/spec 面，尚未 CLI 化（[Day 15] 會標清楚）。

把這些講在前面，是因為選型最怕的就是「用了才發現邊界」。

一張決策表：照你的約束勾

| 你的約束 | 建議方向 |
|---|---|
| 純前端／全端框架，要最順體驗，不在意資料落地 | **Vercel** |
| 後端小服務要快，不想碰基礎設施，能接受代管 | **Railway** |
| 客製與控制需求極高，有專門平台團隊養它 | **自建 K8s** |
| 重度用 AI CLI，且要 self-host / 資料落地 / 台幣計費 | **0ops** |
| 想要 K8s 的自主，但不想付 K8s 的維護心力 | **0ops** |

一個判斷原則

再強調一次 [Day 3] 的精神：**對照要用你的使用情境當軸，不是用功能清單當軸。**

Vercel 功能不比 0ops 少，K8s 能調的旋鈕更是多到爆——但「功能多」從來不是選型的答案。答案是「哪個對到我最大的約束」。你是要體驗（Vercel）、要快（Railway）、要控制（K8s）、還是要 AI 原生＋自架＋在地（0ops）？想清楚約束，答案就在表裡。

總結

今天我們用 AI 原生接入、self-host、計費在地化、學習曲線四個軸，把 0ops 和 Vercel、Railway、自建 K8s 做了對照。結論不是誰全勝，而是各有主場：Vercel 贏體驗、Railway 贏後端速度、K8s 贏控制、0ops 贏「AI 原生＋可自架＋台幣」的交集。同時我們也誠實列了 0ops 的邊界。

選型聊完，明天 [Day 6] 我們回到 0ops 內部，看它「一套後端、兩個入口」的設計：人類用 `0ops` CLI、AI 用 `0ops-mcp`，同一件事兩種做法，權限與保證卻完全一致。
