前言

前面五天（[Day 12]–[Day 15]），我們都是「你一個人」在操作：部署、看 log、redeploy、綁網域。但真實專案幾乎都是團隊在跑——你會需要把同事拉進來、給他適當的權限，也可能得把離開的人移出去。今天就把 0ops 的團隊協作講清楚。

成員變更是敏感操作，所以邀請與移除都走 [Day 4] 講過的 **preview → confirm** 兩階段。今天要做的三件事：

- 用 `0ops teams list` 看你在哪些團隊、擔任什麼角色，並用 `teams use` 切換預設團隊；
- 用 `preview-invite` → `invite` 兩階段邀請新成員；
- 認識 owner / admin / member / viewer 四種角色的差異，以及怎麼移除成員。

看團隊與切換預設團隊

先搞清楚你自己在哪。`0ops teams list` 列出你所屬的所有團隊：

```sh
$ 0ops teams list
```

```
TEAM_SLUG  TEAM_NAME     ROLE   PLAN
acme       Acme Inc.     owner  pro
side       Side Project  member free
```

四個欄位：`team_slug`、`team_name`、你在該團隊的 `role`、以及該團隊的 `plan`。如果你同時屬於多個團隊，可以用 `teams use` 指定預設團隊，之後的指令就不用每次都加 `--team`：

```sh
$ 0ops teams use acme
```

（各群組指令也都支援全域旗標 `--team <slug>` 臨時指定，不改預設。）

邀請成員：preview → confirm 兩階段

邀請新成員分兩步。第一步 `preview-invite` 產生一份邀請計畫，讓你先看清楚「要邀誰、給什麼角色」：

```sh
$ 0ops members preview-invite --role member --github-login alice
```

`--role` 預設是 `member`；被邀請的人可以用 `--github-login` 指定 GitHub 帳號，或用 `--email` 指定信箱。這一步不會真的送出邀請，它回給你一個 `preview-id` 與計畫摘要：

```
PREVIEW_ID   inv_prev_7a3c...
ROLE         member
GITHUB_LOGIN alice
ACTION       將邀請 alice 以 member 身分加入 team acme
```

第二步，確認無誤後帶著這個 `preview-id` 正式送出：

```sh
$ 0ops members invite --preview-id inv_prev_7a3c...
```

這道兩階段閘跟部署、刪除是同一套設計：**先攤開要做什麼，你點頭了才執行**。AI 端對應的是 `invite_member_preview` → `invite_member` 兩個工具，agent 一樣要先展示 preview 取得你同意，才呼叫 confirm。

四種角色與能力差異

0ops 的角色分四級。這裡給一個概念性的能力遞減概覽（實際細部權限以 spec 與 RBAC 定義為準，[Day 22] 會用能力矩陣展開）：

| 角色 | 大致能做什麼 |
|---|---|
| owner | 團隊最高權限：成員/計費/敏感設定，含集中撤權（`sso deprovision`） |
| admin | 管理 app 與成員、可查全團隊稽核（`query_audit_log` 全團隊需 admin） |
| member | 日常部署操作：建立/部署/看 log 等 |
| viewer | 唯讀為主；查稽核時只能看 `actor=me`（且脫敏） |

挑角色的原則是**最小權限**：日常開發的同事給 member 就夠，只需要看狀態的給 viewer，真正要管團隊的才給 admin/owner。權限開得越克制，出事的面越小。

移除成員：一樣走 preview → confirm

人員會流動，移除成員跟邀請對稱，也是兩階段。先 `preview-remove` 指定要移除的使用者：

```sh
$ 0ops members preview-remove --user-id usr_01J...
```

（要拿 `user-id`，先用 `0ops members list` 查，它會列出每個成員的 `user_id` / `github_login` / `email` / `role`。）確認計畫後帶 `preview-id` 執行：

```sh
$ 0ops members remove --preview-id rm_prev_9f2d...
```

移除是把人踢出團隊的敏感操作，所以刻意不給你「一步到位」的捷徑——**先 preview 看清楚要移除誰，再 confirm**。AI 端對應 `remove_member_preview` → `remove_member`。

要補一句狀態說明：如果你的需求是「一個人離職，要一次撤掉他在整個團隊的存取 + 所有 token」，那屬於**集中撤權**，用的是 owner-only 的 `0ops sso deprovision --user <email|id> --yes`，不是這裡的 `members remove`。SSO/OIDC 相關能力（含 deprovision）目前狀態是：OIDC 已有 compose e2e，SAML 細節見 spec，SOC2/DPA 仍規劃中——這些留到 [Day 28] 專門談，今天不展開。

總結

今天我們把 0ops 從單人擴到團隊：`teams list` / `teams use` 看與切團隊，`preview-invite` → `invite` 兩階段邀成員，`preview-remove` → `remove` 兩階段移除，角色分 owner / admin / member / viewer 且遵循最小權限。核心原則是——**成員變更是敏感操作，一律先 preview 再 confirm**。明天 [Day 17]，我們回到 app 本身，講生命週期管理：列出、查詳情，以及最需要謹慎的安全刪除。
