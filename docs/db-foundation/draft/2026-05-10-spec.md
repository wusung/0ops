# Feature Spec：db-foundation

> **狀態**：draft
> **來源**：`docs/0ops-plan.md`「Go 技術棧」「專案結構」「DB schema」段；`docs/agents-guide.md` §3.1、§5.3；ADR-0001（team 邊界與 query 防線）；`tasks/todo.md` M0.2
> **適用範圍**：M0.2 的 Postgres 存取地基；含 `pgxpool` 初始化、`sqlc` codegen、第一個最小 repository、DB integration smoke test、`goose create` 開發 runbook
> **對應 Milestone**：M0.2（M1 read-only chain 動工前的 DB 基礎設施）

## 1. 結論（先讀本段）

- `internal/server/db/` 成為 backend 唯一 DB 存取入口：封裝 `pgxpool`、`sqlc` 生成查詢、repository 包裝與 transaction helper
- `sqlc` 為唯一 query codegen 工具；生成碼固定落在 `internal/server/db/sqlc/`，上層不得直接 import generated row 當 wire DTO
- 第一批 `sqlc` query 只做 **team / membership 的最小 read path**：
  - `ListUserTeams`
  - `CheckTeamMembership`
- `ResolveTeamBySlug` 保留在 repository 內以手寫 `pgx` 查詢實作，不進 `sqlc`，避免把「resolve team 前置例外」誤擴張成一般 query 規則
- 第一個 repository 僅服務 M0.2 smoke test 與未來 M1 middleware / `/v1/me/teams`，不提前偷做 app/domain/deploy 查詢
- `ResolveTeamBySlug` 是唯一可不帶 `team_id` 的 DB 讀取例外，且只能用在 `ResolveTeam` 之前；其他 team-scoped resource query 一律強制 `WHERE team_id = $1`
- `goose create` workflow 要落 runbook，避免每次手動猜命名、驗證步驟或忘記同步更新 `sqlc`
- `M0.2` 驗收以真 Postgres integration test 為準，不接受只用 mock 驗 repository

## 2. 範圍

### 2.1 包含

- `internal/server/db/` package scaffold
- `pgxpool` config 與 connect / ping / close lifecycle
- `sqlc.yaml` 與 codegen 輸出位置約定
- 第一批 team / membership read query
- `ResolveTeamBySlug` 之受限例外查詢
- repository 封裝與 domain struct mapping
- DB integration smoke test（migration 後真實查詢）
- `goose create` runbook
- `Makefile` 增加 `sqlc` target 與必要 test target 調整

### 2.2 不包含

- HTTP router / handler
- auth middleware chain
- CLI / MCP client
- app/domain/deploy 的 read query
- preview/confirm write path
- 新的業務 migration（除非為支援 DB foundation 本身不可避免）

## 4. DB 契約

### 4.1 Config

`config.go` 定義最小設定：

```go
type Config struct {
    URL             string
    MaxConns        int32
    MinConns        int32
    MaxConnLifetime time.Duration
    MaxConnIdleTime time.Duration
}
```

來源優先序：

1. 明確傳入 `Config`
2. 環境變數 `DATABASE_URL`
3. 其餘 pool 參數用保守預設

M0.2 預設值：

| 欄位 | 值 |
|---|---|
| `MaxConns` | 10 |
| `MinConns` | 0 |
| `MaxConnLifetime` | 30m |
| `MaxConnIdleTime` | 5m |

> 理由：M0 階段只有單 backend、單測試程序；先用保守值，避免過早綁死 M5 的 HA / Pg sizing。

### 4.2 `db.go`

提供三個最小入口：

```go
func NewPool(ctx context.Context, cfg Config) (*pgxpool.Pool, error)
func MustPing(ctx context.Context, pool *pgxpool.Pool) error
func NewQueries(pool DBTX) *sqlc.Queries
```

其中 `DBTX` 與 `sqlc` 生成介面對齊，為未來 transaction / tests 留鉤子。

### 4.3 Repository 邊界

`repository.go` 不把 sqlc row 洩漏到外層。對外先提供：

```go
type Repository struct {
    pool    *pgxpool.Pool
    queries *sqlc.Queries
}

func NewRepository(pool *pgxpool.Pool) *Repository

func (r *Repository) ResolveTeamBySlug(ctx context.Context, slug string) (Team, error)
func (r *Repository) ListUserTeams(ctx context.Context, userID string, limit int32, afterSlug *string) ([]TeamMembership, error)
func (r *Repository) CheckTeamMembership(ctx context.Context, teamID string, userID string) (bool, error)
```

### 4.4 Domain struct

```go
type Team struct {
    ID         string
    Slug       string
    Name       string
    Plan       string
    ArchivedAt *time.Time
}

type TeamMembership struct {
    Team       Team
    UserID     string
    Role       string
    JoinedAt   *time.Time
    InvitedAt  *time.Time
}
```

> M0.2 不先引入 `internal/shared/rbac` 的 typed role，因該 package 尚未落地；repository 先保持資料層中立。M0 末做 shared contract 時再收斂。

## 5. Query 設計

### 5.1 `sqlc` Query 清單

```sql
-- name: ListUserTeams :many
SELECT
  t.id,
  t.slug,
  t.name,
  t.plan,
  t.archived_at,
  tm.user_id,
  tm.role,
  tm.joined_at,
  tm.invited_at
FROM team_membership tm
JOIN team t ON t.id = tm.team_id
WHERE tm.user_id = $1
  AND ($2::citext IS NULL OR t.slug > $2)
ORDER BY t.slug
LIMIT $3;

-- name: CheckTeamMembership :one
SELECT EXISTS (
  SELECT 1
  FROM team_membership
  WHERE team_id = $1
    AND user_id = $2
);
```

### 5.2 Repository 例外查詢

`ResolveTeamBySlug` 不走 `sqlc`，而是在 repository 內用手寫 `pgx` 查詢：

```sql
SELECT id, slug, name, plan, archived_at
FROM team
WHERE slug = $1;
```

限制：

- 只能由未來 `ResolveTeam` middleware 或其前置 helper 使用
- 不得複製成一般用途 helper
- 不得擴張成 `ListTeamsByPlan`、`ListAllApps` 這類跨 team 掃描查詢

### 5.3 邊界判斷

- `ResolveTeamBySlug` 合法，但它不是 `sqlc` team-scoped query，而是 tenant resolution bootstrap 例外
- `ListUserTeams` 合法，因 `/v1/me/*` 本來就以 `user_id` 為第一層邊界
- `CheckTeamMembership` 合法，因這是 middleware 的 team/user 雙鍵檢查
- **禁止** 在 M0.2 內新增任何像 `ListApps()` 這種不帶 `team_id` 的 team-scoped query，避免把防線打壞

### 5.4 Pagination 簡化

`ListUserTeams` 先用 `slug` cursor 形狀：

- `afterSlug = nil` 表示第一頁
- `ORDER BY t.slug`
- `LIMIT` 由 caller 傳入

M0.2 不先實作通用 cursor codec，因那是 M1 read API vertical slice 的責任。

## 6. `sqlc` 設定

### 6.1 `sqlc.yaml`

M0.2 採單 package、單 schema、單 query file：

```yaml
version: "2"
sql:
  - engine: "postgresql"
    schema:
      - "migrations/00001_init.sql"
    queries:
      - "internal/server/db/queries.sql"
    gen:
      go:
        package: "sqlc"
        out: "internal/server/db/sqlc"
        sql_package: "pgx/v5"
        emit_json_tags: false
        emit_interface: false
        emit_exact_table_names: false
```

### 6.2 Codegen 規則

- 生成碼固定 commit 進 repo，不要求使用者本機每次現生
- `./manage.sh sqlc` 為唯一入口
- 任何 `queries.sql` 修改都必須同步更新 generated files 與測試

### 6.3 `Makefile`

新增：

```make
sqlc: ## 產生 sqlc 程式碼
	sqlc generate
```

若後續需要，可再加 `check-sqlc`；M0.2 先不擴張。

## 7. 測試策略

### 7.1 TDD 順序

1. 先寫 integration test
2. 觀察 fail（缺 package / 缺 queries / 缺 codegen / 缺 connect）
3. 補最小實作
4. 跑綠

### 7.2 Smoke test 範圍

至少四個案例：

1. `NewPool` 能對 migration 後的 Postgres connect + ping
2. `ResolveTeamBySlug` 能 resolve 正確 team
3. `ListUserTeams` 只列出指定 user 的 teams，且順序符合 `slug`
4. `CheckTeamMembership` 對存在 / 不存在組合回正確布林

### 7.3 測試環境

M0.2 優先重用 compose stack Postgres，不引入 testcontainers。

測試前提：

- `./manage.sh dev` 已起 `db` 並跑完 migration
- 測試用 `DATABASE_URL` 直接連 Postgres

若未來需要無 compose 的自足測試，再另開 spec，不在 M0.2 擴張。

### 7.4 Seed 策略

每個測試用 transaction 包起來，結束 rollback；或使用每測試專屬資料列加 deterministic slug。

M0.2 建議：

- 共用一個 test DB
- 每測試 `BEGIN`
- 插入 `user_account`、`team`、`team_membership`
- `ROLLBACK`

理由：比整庫 truncate 更快，也避免互相污染。

## 8. Goose Create Runbook

runbook 檔案：`docs/runbooks/goose-create-workflow.md`

至少要寫清楚：

1. 建 migration 的唯一入口
   - `goose create <short_name> sql`
2. 命名規則
   - 英文 kebab / snake 皆可，但要短且描述結果，例如 `add_team_plan_check`
3. 建完後的固定步驟
   - 補 `-- +goose Up`
   - 補 `-- +goose Down`
   - 跑 `./manage.sh migrate`
   - 若 query shape 受影響，跑 `./manage.sh sqlc`
   - 補 / 更新 integration test
4. 禁止事項
   - 不可只寫 Up 不寫 Down
   - 不可改舊 migration 檔內容去覆蓋歷史
   - 不可改 schema 後忘記更新 `sqlc` 與測試

## 9. 驗收標準

`M0.2` 完成需同時滿足：

- `sqlc.yaml` 存在且 `./manage.sh sqlc` 可生成程式碼
- `internal/server/db/` 可建立 pool 並執行第一批 query
- `ResolveTeamBySlug` 以 repository 內受限例外存在，未污染 `sqlc` 規則
- repository 不外洩 sqlc row 到外層
- integration smoke test 通過
- `docs/runbooks/goose-create-workflow.md` 存在且步驟完整
- `tasks/todo.md` 的 M0.2 可從未完成改為已完成

1. 加 failing DB integration test skeleton

4. 補 `config.go` / `db.go`

## 11. 風險與限制

### 11.1 風險

- 本機若未先起 compose stack，integration test 會因 DB 不存在失敗
- 目前用 migration 檔當 `sqlc schema` 輸入，後續 migration 變多時 codegen 速度會上升
- role / scope typed enum 尚未落地，repository 暫時只能回 `string`

### 11.2 限制

- M0.2 故意不做 generic pagination / cursor helper
- 不做 write repository
- 不做 transaction helper abstraction beyond `pgxpool` 基礎能力

## 12. 與既有文件對齊

- 對齊 `tasks/todo.md`：M0.2 就是 `pgx + sqlc` 架接與 `goose create` workflow
- 對齊 `docs/agents-guide.md`：DB 固定 Postgres、SQL 存取以 `sqlc + pgx` 為主
- 對齊 ADR-0001：`sqlc` team-scoped query 不可漏 `team_id`；本 spec 把 `ResolveTeamBySlug` 收斂成 repository 內的 bootstrap 例外，避免錯誤擴張成通用豁免

## 13. Open Questions

- `goose create` 是否要再包一層 `./manage.sh migrate-create NAME=...`？M0.2 暫不做，先以 runbook 約束
- integration test 是否要自動跳過「無 DB 可連」情境？M0.2 傾向不跳過，直接 fail，因這是基礎設施 smoke test
